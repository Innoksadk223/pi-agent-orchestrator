Pi Extension · pi-agent-orchestrator

让一队 AI 干活，
你负责签字。

agent_team 不是「一句话丢进去自动完成」的按钮。它是一个控制面：你出目标和验收标准，主 Pi 当 Leader 写计划、派活、解释结果，成员各自开一个独立会话动手。runtime 只记账、守门，从不替任何人点下一步。下面先把机制拆开，再给六种真实用法。

2名起 最少成员数。一名动手的 Coder，加一名只读的 Reviewer。
10个状态 任务在 PENDING 到 VERIFIED 之间流转，其中只有 Reviewer 能写 VERIFIED。
0自动调度 没有「跑完自动接下一单」。每个节点都要 Leader 显式发起。

01谁在指挥谁

先分清三个角色和一本账，后面所有规矩都是从这儿长出来的。

这套东西里没有「老板 AI」替你完成任务。工作被拆成三份：你出目标和验收，主 Pi 出计划和判断，成员出执行。第四样东西是 runtime，它不生产任何决策。

You

你

说清要什么结果、哪些文件可以动、怎么算通过。最后验收只有你能签。你不需要会写 plan，但要知道它定了什么。

Main Pi

主 Pi · 唯一 Leader

写计划、派工、解释 Reviewer 的意见、决定重试还是换人还是停手。上下文丢了就以 status 为唯一事实源。

Members

成员 · 独立会话

每个成员有自己的 Session、人格、工具和可写路径。它看不到整个项目的来龙去脉，只看到本轮的局部任务，交回一份报告信封。

runtime 是一本账加一道门

它保存实时状态，校验成员授权、任务依赖、成员忙闲和路径冲突，把结果传回给 Leader。它不做三件事：不选专家、不创建任务、不自动派发下一步。

这条边界是有意留的。多 Agent 最怕的不是算力不够，是没人负责。所有推进点都压在 Leader 一个人身上，出问题时你知道该问谁、该回滚到哪。
决定权归属
这件事谁说了算
要做什么、能改哪些文件、怎么算完成你，在 plan 的确认门里定下来
计划长什么样（名册、依赖、路径、验收）主 Pi 起草，你点同意
这一轮过没过plan 里指定的那一个 Reviewer
下一步跑哪个任务Leader 显式调用 run / parallel / review
任务算不算完成先由 Reviewer 写 VERIFIED，再由你 HUMAN_ACCEPT
自动重试、自动熔断、自动接下一单没有这个功能。告警只告警，绝不自动动手

顺带一个容易忽略的事实：成员是同一个账号、各自带 bash 的独立进程。它不是一个被沙箱锁住的函数。这决定了后面「路径授权」那节的调性——那是声明，不是牢门。

02一次注册的计划

复杂任务不许边干边加人。开工前一次把名册、裁决者、依赖、写权限、验收全部固定。

所有派工都要先注册一份 plan。runtime 拒绝「没规划就直接跑」的调用，也拒绝在计划外用 inline 参数临时塞一个成员或任务。计划一旦注册，后续每轮只按 taskId 推进，不再重新描述需求。

members[]

名册。只增不减。每名成员有 id、kind、role、一份完整的角色书，可选指定模型、思考程度和工具白名单。

reviewerId

唯一裁决者。全队只有这一个成员能写下 VERIFIED 或 FIX_REQUIRED。

tasks[]

任务图。每个任务挂一名成员、一条依赖关系（dependsOn）、一组可写路径（ownedPaths）、一组局部验收标准。

acceptance[]

全局完成标准。Reviewer 的最终验证要对照它，你签字时也对照它。

最小可用的两人团队 · plan
agent_team({
  action: "plan",
  team: "default",
  plan: {
    members: [
      {
        id: "coder",
        kind: "coder",
        role: "后端实现工程师",
        instructions: "你是本团队的资深后端工程师，专精 TypeScript 与 Node 运行时。"
          + "职责：只实现 TaskPacket 内 owned paths 的改动，动手前先读调用方。"
          + "边界：不碰他人文件，不做架构决策。风格：代码优先、行文极简。"
          + "需求模糊时返回 BLOCK 并附问题，不猜测。结尾按约定输出执行 JSON envelope。"
      },
      {
        id: "reviewer",
        kind: "reviewer",
        role: "独立评审",
        instructions: "你是团队的独立质量门：怀疑一切、只认证据，仅对判定结果负责。"
          + "边界：只读，绝不编辑文件。风格：严格对照 acceptance 逐条核验。"
          + "通过 review envelope 输出判定；FIX_REQUIRED 必须附可执行的 fix_prompt。",
        tools: ["read", "grep", "find", "ls"]
      }
    ],
    reviewerId: "reviewer",
    tasks: [{
      id: "impl",
      memberId: "coder",
      objective: "把会话过期时间从硬编码改成读环境变量，默认值保持不变",
      constraints: ["不改公开函数签名"],
      dependsOn: [],
      ownedPaths: ["src/session"],
      acceptance: ["SESSION_TTL 未设置时行为与改动前一致"],
      relevantPaths: ["src/session/store.ts"]
    }],
    acceptance: ["Reviewer 最终验证通过后，由用户执行 HUMAN_ACCEPT"]
  }
})

五类成员，各管一件事

coder 写代码，唯一默认带 MCP 的角色 reviewer 判过不过，唯一能写 verdict debugger 只读诊断 product 只读产品视角 optimizer 只读优化候选，只接已通过的成果

后三种只能通过 expert 通道出场，不写 verdict、不取写权限。只读角色默认拿不到 MCP，要在计划里逐个点名具体的 mcp__server__tool 才会给——这样「只读」不会因为默认能力被静默放大。

instructions 是成员唯一的人格来源

它会原样注入成员进程。写一句话「你是工程师，帮我写代码」的结果，是成员每一轮都在猜你的标准。一份能用的角色书要写清五件事：职责与专长、边界（不碰什么、不决策什么）、行事风格、输出要求、和其他成员怎么配合。

改指令不会改写历史。成员会话按 Session 复用，旧上下文仍然主导输出。想改一个已经跑歪的成员，正确做法是 kill 掉、用 amendment 加一名替补（新 Session、新角色书），把任务和 reviewerId 切过去；反复重发同一个提示词，大概率复现同一个错误。

先复用，再新增

新增成员的成本比看起来高：多一个 Session、一份角色书、一次确认门，而且名册永远删不掉。所以在加人之前先回答一句：「现有成员的 kind、角色书和权限边界，为什么盖不住这件事？」答不上来，就把新任务派给既有成员。

03成员看到的授权地图

成员读不到你写的完整需求。它每轮看到的是一张图：队友是谁、各自能写哪儿、谁终裁。

每次派发，提示词的第一段都是同一张队内地图（[TEAM SCOPE]）。它不是背景介绍，而是成员判断「这件事该不该我做、这个文件该不该我改」的唯一依据。

派发首段 · 以 reviewer 的视角（内容按你的 plan 生成）
[TEAM SCOPE]
- coder — coder · 后端实现工程师 — owns: src/session
- reviewer: reviewer
联系与同伴消息不授予写入权，也不改变这张图。
[/TEAM SCOPE]

每行一句话给全三样：谁是队友（id、kind、角色）、他能写到哪里（该成员全部任务 ownedPaths 的并集，没有任务就写 none）、以及最后单独一行的终裁者。名册按 id 排序，跳过自己与已停止的成员，超过 12 人只保留前 11 行并追加「…另有 N 位见 status」。图每轮重建，不进缓存，所以它总是当下的事实。

想让成员守边界，靠的是这张图里的 ownedPaths 写准确，不是靠 instructions 里叮嘱十遍。反过来，末行那句「联系与同伴消息不授予写入权」也在同一张图里——能发消息不等于能写对方的文件。

ownedPaths 是声明，不是沙箱

成员和你是同一个系统账号，各带 bash。模型层拦不住越界写，实际能做的只有事后审计：每轮结束时 runtime 比对前后两次 git status，把 ownedPaths 之外新增的路径记成一条 workspace warning 交回 Leader。只告警，不回滚，不阻断；非 git 工作区根本检测不到。

所以路径写细一点不是为了流程好看，是为了让这条告警有信号。写 src 这样的目录范围，等于放弃了这项检查。

04手动循环

一条主线，一个回环。每一跳都得有人按，按的人永远是 Leader。

01 plan 注册名册、依赖、写权限、验收
02 run / parallel 派一个，或派一整批
03 SUBMITTED 成员交回报告信封
04 review 唯一裁决者出场
05 VERIFIED 通过；不通过就同一任务返工
06 HUMAN_ACCEPT 你签字，再由 Leader 调 close

FIX_REQUIRED 不新建任务：同一个 taskId 开下一个 attempt，Reviewer 的 fix_prompt 原样带回去。

五条硬规则

  • 只有 SUBMITTED 能被审。Reviewer 看不到正在跑的任务，也审不了还没交的东西。
  • 只有 VERIFIED 和 CANCELED 释放写锁。任务从 RUNNING 到你验收之前，路径一直被它占着，别人碰不了。
  • VERIFIED 会把下游点亮成 READY。依赖关系靠状态流转，不靠人记。
  • parallel 有三条硬约束：同批成员互异、依赖都已 VERIFIED、路径两两不冲突（相等或父子包含都算冲突）。一批最多 8 个任务。
  • 并行里有一次启动失败，同批其余 attempt 会被中断，并等它们离开运行态。没有「部分成功继续跑」。
后台派发成功接受后，Leader 的当前回合就结束、把输入权还给你，成员继续在后台跑。跑完后它会收到一条精简通知——通知不是调度，下一步仍然要它显式调用。

05报告信封与任务状态

成员怎么交差、交不成会怎样、十个状态分别归谁写。

成员可以写很长的正文给人看，但最后一个非空行必须是一行裸 JSON。runtime 只认这个信封，绝不从正文里猜状态。三种形状：

execution执行回报
{"agent_team_report":{"type":"execution","taskId":"impl","status":"SUBMITTED","summary":"会话 TTL 迁到环境变量，默认值 30 分钟保持不变","evidence":["src/session/store.ts:42"],"requests":[]}}
review评审判定
{"agent_team_report":{"type":"review","reviewRoundId":"review-1","summary":"一处默认值仍然硬编码","evidence":["src/session/store.ts:58"],"requests":[],"decisions":[{"taskId":"impl","verdict":"FIX_REQUIRED","fix_prompt":"store.ts:58 的默认值仍是硬编码 1800，改为先读 env 再回退"}]}}
expert只读结论
{"agent_team_report":{"type":"expert","expertRoundId":"diag-1","summary":"迁移本身没问题，重复报错来自空表","evidence":["src/session/store.ts:96"],"requests":[]}}
  1. 裸行，不加围栏。不能包在 ```json 里，前面不留空行、后面不留注释。小模型特别容易照抄示例里的围栏。
  2. evidence 用 path:line。正斜杠，纯中文描述，不写「第 42 行」，不贴代码片段。
  3. summary 只写一句判定式结论。做了什么、结果数字。正文才是给人读的部分。
  4. Coder 不能自报 VERIFIED。执行信封只有两个合法状态：SUBMITTED 和 BLOCKED。

信封坏了会怎样

缺失、损坏、越界、ID 对不上，一律进 REPORT_INVALID：正文和写锁都保留，通知 Leader，不自动重试。处理方式是拿同一个 taskId 重派一次新 attempt，让它重新核对自己的产出。连坏两次，就该考虑换人而不是继续重试。

十个状态

任务状态机
状态意思谁能写进去
PENDING依赖还没通过，等着runtime
READY可以派工了runtime（依赖转 VERIFIED 时）

06上手六步

第一次用，照着这个顺序走一遍。每步下面写着「这一步该看什么」。

00LOAD

先把工具装上身

agent_team 是按需加载的：新会话里默认没有它。要么让主 Pi 搜一次，要么你自己敲命令。

两种方式，任选其一
tool_search({ query: "agent_team" })   # 模型侧检索，下一轮声明
/team activate                         # 你自己敲，立刻声明

看到工具出现在可用列表里，才继续下一步。没有它的时候直接说「用 agent_team 帮我组队」，主 Pi 会先检索。

01BRIEF

把目标交代清楚

不需要背字段名，但这四件事得说到：要什么结果、哪些文件可动、怎么算通过、要不要独立评审。

缺一样，Leader 就会替你猜——而它猜出来的东西会直接写进计划，变成成员的行动依据。

02GATE

在确认门里看一眼计划

第一次注册会弹一次确认（auto 关闭时）。窗口里能滚动看完整计划，Enter 确认、Esc 拒绝。只看四个地方：

  • 名册里的人够不够、对不对口——有没有该有却没有的评审者。
  • ownedPaths 是不是具体路径——写成一个大目录就等于关掉了越界检查。
  • reviewerId 指向谁——它将是唯一能判过的人。
  • acceptance 能不能判真假——「代码质量良好」判不了，「默认值不变」能判。
03RUN

派工

单个 / 整批
agent_team({ action: "run", taskId: "impl" })
agent_team({ action: "parallel", taskIds: ["docs", "api"] })

派工前 runtime 会做完整预检：schema、revision、依赖、成员可用性、路径冲突。预检不过就不会有任何成员被唤醒。

04REVIEW

审，然后决定返工还是放行

一轮评审
agent_team({ action: "review", reviewRoundId: "review-1", taskIds: ["impl"] })

拿到 FIX_REQUIRED 就直接 run 同一个 taskId，Reviewer 的原话会随包带到 Coder 面前。你不是在转述意见，是在传递原文。

05WATCH

想看现场就开面板

命令
/team open        # 唤回 Dashboard，只读，不启动任何 child
/team status      # 成员/任务计数、当前对象、阻塞、待答请求

协作图只显示类型和状态，不显示正文和凭据。节点上的涌动只证明运行时接受了投递，不证明对方读过，更不等于通过。面板能停、能继续、能换模型，但不能派活。

06SIGN

你签字，然后收尾

Reviewer 的 FINAL_VERIFY: VERIFIED 只代表「Agent 证据完整」，不等于你验收。看完证据和限制后，再决定收尾。

收尾
agent_team({ action: "close", team: "default" })

非 auto 会话里，close 还会再问一次，而且这次不设倒计时——等不出来，只能明确点同意或拒绝。

07六种用法

从最常见的开始。每种都写清：什么时候进来、怎么发、结果落在哪、有一个什么坑。

01

一个不太小的改动

最常见的一种。你有一个说得清、但一个人做完容易漏边的活：迁移配置、改一处协议、补一段状态机。想要一个动手的，加一个挑错的。

coder→reviewer

注册 + 派工 + 评审
agent_team({
  action: "plan", team: "default",
  plan: {
    members: [coder, reviewer],
    reviewerId: "reviewer",
    tasks: [{ id: "impl",
      memberId: "coder",
      ownedPaths: ["src/session"] }],
    acceptance: ["默认值不变"]
  }
})

agent_team({ action: "run",
  taskId: "impl" })

agent_team({ action: "review",
  reviewRoundId: "review-1",
  taskIds: ["impl"] })

结果落在哪：通过后任务变 VERIFIED，写锁释放；下游任务自动变 READY。不通过就拿到一条 fix_prompt，run 同一 taskId 再来一次。

坑：两个人是最小配置，不是可选项。members 少一个就直接过不了校验。只有 coder 没有 reviewer，等于没有判定来源。

02

两件互不相干的事

两份工作既不共享文件，也不需要谁等谁。比如一个改 API、一个补文档——两个 coder，各占一条路径。

coder+coder+reviewer

并行派发
agent_team({ action: "parallel",
  taskIds: ["api", "docs"] })

结果：两个成员同时开工，各自独占自己的路径。坑：同一名成员不能同时接两个并行任务；路径哪怕父子包含也算冲突。

03

卡住了，要人帮着看

同一个成员连续两次交不出合格结果，或者你怀疑方向本身有问题。这时候需要的是一双只读的眼睛，不是一个新任务。

debugger·只读·不写 verdict

只读专家
agent_team({
  action: "expert",
  expertRoundId: "diag-1",
  expertId: "debugger",
  taskIds: ["impl"],
  objective: "定位同一处默认值为何连续改错"
})

结果：一份 expert 信封，带证据和结论，不改任务状态。坑：专家必须事先在计划里批准；optimizer 只接已经 VERIFIED 的成果。

04

只想问一句

你需要一个判断，但不需要开一轮评审、更不想动任何任务。比如问 Reviewer 某个决定为什么反复出问题。

任意已规划成员·空闲即可

只读提问
agent_team({
  action: "consult",
  member: { id: "reviewer" },
  objective: "impl 为什么连续两次交不上信封？"
})

结果：后台跑一轮，回来一个 expert 形状的信封，轮次 id 还叫 expertRoundId。任务状态前后不变。坑：「只读」是契约层面的，被咨询的成员手里仍然有写工具。

05

不想每次都被确认门拦住

你已经反复跑过、信任这套流程，只想让它一口气走完。

顺序很重要
agent_team({
  action: "set-auto", auto: true })

// 然后才发 plan

结果：plan 门被跳过，开关持久化，新会话沿用。坑：门已经弹出来之后再补 auto 是无效的，那次确认撤不回来。而且 auto 也不会替你填 VERIFIED 和 HUMAN_ACCEPT。

06

干到一半想改方向，或者想收手

成员的活还在跑，但你发现范围不对；或者你想先看看现场，再决定放不放。四个动作各管一段，别混着用。

steer·pause·resume·cancel

改方向 / 停
// 只对正在运行的成员
agent_team({ action: "steer",
  member: { id: "coder" },
  message: "只改 src/session" })

// 软中断，保留会话
agent_team({ action: "pause",
  taskId: "impl" })
继续 / 放弃
// 同一目标，新 attempt
agent_team({ action: "resume",
  taskId: "impl" })

// 只放弃还没在跑的
agent_team({ action: "cancel",
  taskIds: ["dropped"] })

结果：pause 后成员记为 INTERRUPTED、任务记为 BLOCKED 且不重放；resume 走完整的重新派发预检。坑：cancel 撤不回 RUNNING；已经在审的任务要先走完评审循环。

换模型

  • 只允许空闲成员先 stop
  • 网页切换不追问Leader 要确认
  • 首轮核对模型不符即失败

回答成员的提问

  • 成员上行 leader登记为请求
  • steer 实时回运行中
  • answer-request下次派发注入

08六个坑

按踩中的频率排序。前两个几乎每个新手都会撞一次。

  1. 把信封包进了代码围栏

    成员用 Markdown 代码块把 JSON 包起来，runtime 不认，直接 REPORT_INVALID。要的是最后一个非空行、裸的单行 JSON，不加围栏、不缩进成块。小模型尤其容易照抄示例里的围栏，所以示例里一个都不写。

  2. 以为改 instructions 就能纠正成员

    会话按 Session 复用。改了角色书，旧历史仍然主导输出，重发同一个提示词大概率复现同一个错误。kill 掉、用 amendment 加一名替补，才是干净的做法。

  3. 让同一名成员同时接两个并行任务

    parallel 要求同批成员互异。两条任务挂同一个成员时，第二批会被拒——不是 bug，是因为一个人不能同时在两个地方改代码。

  4. 把 ownedPaths 当成沙箱

    它只是声明。成员同账号、带 bash，越过路径照样能写。实际防线只有事后 git status 比对的一条告警：不回滚、不阻断，非 git 工作区还检测不到。真要隔离，得靠 OS 级沙箱，这层目前没有。

  5. 确认门弹出来之后才想起开 auto

    顺序错了。门一旦弹出，那一次确认就必须由你处理；此时再 set-auto 只能影响下一次。想要全自动，先开关再发 plan。

  6. 想删掉一个没用的成员

    名册只增不减。换方向靠改任务、改授权、加替补，不能删。所以加人之前那句「为什么现有成员盖不住」值得认真回答——它决定的是长期成本。

所有动作都在 agent_team({ action, ... }) 里。一个动作只接自己的字段，混着传会报错。
